# selfsync

[English](README.md) · **Русский**

Синхронизация vault'а Obsidian через свой сервер. Один небольшой бинарник на Rust, данные в SQLite и файлах, плагин для Obsidian на десктопе и телефоне, консольный клиент для серверов и NAS.

Главное обещание: **ни одна правка не теряется молча.**
- Правки в разных местах файла сливаются сами (diff3).
- При пересекающихся правках обе версии остаются: серверная на месте, ваша — копией рядом.
- Правка побеждает удаление.
- Удалённое на любом устройстве хранится в корзине сервера, у каждого файла есть история ревизий.

Возможности:
- переименования и перемещения без повторной загрузки;
- большие файлы с докачкой в обе стороны;
- регистронезависимые ФС (Windows, macOS, iOS, Android) и имена в Unicode (NFC/NFD);
- сквозное шифрование содержимого и имён;
- подключение нового устройства по ссылке или QR-коду;
- отзыв устройств.

## Перед установкой плагина

- **Нужен свой сервер selfsync.** Без него плагин ничего не делает: облачного сервиса, аккаунта и подписки нет.
- **Сеть.** Плагин обращается только к адресу сервера из настроек: передаёт файлы vault'а и их метаданные (имена, размеры, время изменения). Без шифрования сервер хранит заметки как есть, с шифрованием — только шифртекст.
- **Телеметрии нет.** Больше плагин никуда ничего не отправляет.
- **Прямой доступ к файловой системе на десктопе.** Ревью каталога Obsidian об этом предупреждает, поэтому объясняем. На десктопе плагин читает и пишет файлы vault'а через модуль `fs` из Node, а не через API Obsidian: скачанный файл заменяет старый атомарно и сбрасывается на диск (`fsync`), так что сбой или отключение питания не оставят недописанную заметку, а большие вложения читаются и хэшируются частями, а не целиком в память. Плагин работает только с путями внутри папки vault'а (и с корзиной Obsidian при удалении). На телефонах — через адаптер Obsidian.
- **Буфер обмена.** Кнопка «Скопировать ссылку» в окне «Подключить новое устройство» кладёт одноразовую ссылку в буфер. Читать буфер плагин не умеет.
- **WebAssembly внутри `main.js`.** Ядро синка — Rust, скомпилированный в WebAssembly ([crates/selfsync-wasm](crates/selfsync-wasm)) и встроенный в минифицированный `main.js`. Ничего не обфусцировано и не скачивается во время работы: файлы релиза собирает из этого репозитория [релизный workflow](.github/workflows/release.yml), к ним приложены аттестации происхождения GitHub.
- Удалённое уходит в корзину Obsidian (системную или `.trash/`, как настроено в Obsidian) и никогда не стирается безвозвратно.

## Как это устроено

```
 Obsidian (десктоп, телефон)        папка на сервере/NAS
 ┌──────────────────────────┐       ┌──────────────────┐
 │ плагин (TypeScript)      │       │ selfsync-cli     │
 │  ввод-вывод и интерфейс  │       │  tokio + std::fs │
 │ ┌──────────────────────┐ │       │ ┌──────────────┐ │
 │ │ ядро синка (WASM)    │ │       │ │ ядро синка   │ │
 │ └──────────────────────┘ │       │ └──────────────┘ │
 └────────────┬─────────────┘       └────────┬─────────┘
              │      HTTP + protobuf         │
              └──────────────┬───────────────┘
                     ┌───────┴────────┐
                     │ selfsync       │  SQLite (метаданные, история)
                     │ (сервер)       │  + блобы по хэшу
                     └────────────────┘
```

Логика синка написана один раз — в ядре `selfsync-core`. Плагин и консольный клиент только исполняют его действия: прочитать файл, записать, отправить запрос. Подробнее — в [spec/architecture.md](spec/architecture.md), протокол — в [spec/protocol.md](spec/protocol.md), принятые решения — в [spec/decisions.md](spec/decisions.md).

## Сервер

### Какой режим выбрать

Сервер — один бинарник `selfsync`, который умеет работать по-разному. Различие в том, сколько он потребляет, когда никто не синхронизируется, и как быстро правка с одного устройства появляется на другом.

| Режим | Процесс между синками | Как узнаёт о чужих правках | Когда подходит |
|---|---|---|---|
| **CGI** (Caddy, nginx + fcgiwrap) | нет, процесс на каждый запрос (~1 мс старта) | опрос: каждые 15 с, пока Obsidian активен; в простое реже, до 5 мин | общий хостинг, минимум ресурсов |
| **socket** (systemd socket activation) | поднимается по первому запросу, выходит после 10 мин простоя | long-poll `/v1/wait` — почти мгновенно | свой VPS: быстро и почти ничего не стоит в простое |
| **serve** (Docker, обычный процесс) | работает всегда | long-poll | Docker, домашний сервер |
| **serve + Sablier** (Docker по требованию) | контейнер поднимает прокси, гасит Sablier | опрос | Docker с экономией памяти |
| **Podman Quadlet** | как socket, но в контейнере | long-poll | rootless-контейнер |

**Опрос или запуск по требованию — компромисс.** Long-poll держит открытым запрос к серверу, пока Obsidian на переднем плане. В режиме socket это продлевает жизнь процесса: он завершится через 10 минут после того, как все устройства уйдут в фон. Если важнее, чтобы процесса не было почти никогда, выключите в плагине «Сервер работает постоянно». Тогда клиенты будут опрашивать сервер, а чужие правки станут приходить с задержкой до интервала опроса. Для CGI этот переключатель должен быть выключен: там long-poll невозможен (клиент заметит это сам и перейдёт на опрос).

### Установка бинарника

Готовые статические бинарники (musl, x86_64 и aarch64) лежат в релизах `server-X.Y.Z` вместе с `SHA256SUMS` и аттестациями происхождения (в релизах `X.Y.Z` — только плагин Obsidian):

```sh
sha256sum -c SHA256SUMS --ignore-missing
gh attestation verify selfsync-x86_64-unknown-linux-musl --repo Darkildo/selfsync
sudo install -m 0755 selfsync-x86_64-unknown-linux-musl /usr/local/bin/selfsync
```

Сборка из исходников: `cargo build --release -p selfsync-server` (бинарник `target/release/selfsync`).

### systemd: запуск по требованию (socket)

```sh
sudo cp deploy/systemd/selfsync.{socket,service} deploy/systemd/selfsync-{sweep,verify}.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now selfsync.socket selfsync-sweep.timer selfsync-verify.timer
```

Перед сервером нужен обратный прокси с TLS. Готовые конфиги: [deploy/caddy/Caddyfile.socket](deploy/caddy/Caddyfile.socket) и [deploy/nginx/selfsync-proxy.conf](deploy/nginx/selfsync-proxy.conf). Юнит запускается с `DynamicUser`, данные лежат в `/var/lib/selfsync`. Служебные команды выполняются так:

```sh
sudo systemd-run --pipe -p DynamicUser=yes -p User=selfsync -p StateDirectory=selfsync \
  /usr/local/bin/selfsync token add --vault notes --name laptop
```

### CGI

[deploy/caddy/Caddyfile.cgi](deploy/caddy/Caddyfile.cgi) (Caddy с плагином `caddy-cgi`) или [deploy/nginx/selfsync-cgi.conf](deploy/nginx/selfsync-cgi.conf) (nginx + fcgiwrap). Режим CGI включается сам по `GATEWAY_INTERFACE`. Каталог данных должен принадлежать пользователю, от которого запускается CGI, и служебные команды нужно выполнять от него же.

### Docker

```sh
cd deploy
mkdir -p data && sudo chown 65532:65532 data   # bind mount, не именованный volume
docker compose --profile always up -d           # или --profile ondemand (Sablier)
docker compose run --rm selfsync token add --vault notes --name laptop
```

Образ основан на distroless/static: в нём нет оболочки, файловая система только для чтения, процесс работает без привилегий. Данные хранятся в `./data` через bind mount, а не в именованном volume: именованный volume стирается командой `docker compose down -v` вместе со всеми заметками.

### Настройки

Переменные окружения (или TOML через `--config`; переменные приоритетнее):

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `SELFSYNC_DATA_DIR` | `$STATE_DIRECTORY` или `/var/lib/selfsync` | каталог данных |
| `SELFSYNC_PUBLIC_URL` | из заголовков запроса | внешний адрес — для ссылок подключения |
| `SELFSYNC_IDLE_TIMEOUT` | `10m` (socket) | выход после простоя, `0` — никогда |
| `SELFSYNC_MAX_BLOB_SIZE` | 512 МиБ | наибольший файл |
| `SELFSYNC_MAX_BODY_SIZE` | 16 МиБ | тело запроса (метаданные, часть загрузки); согласуйте с прокси |
| `SELFSYNC_LOG` | `info` | уровень журнала (имена файлов в журнал не попадают) |
| `SELFSYNC_TRUSTED_PROXY` | `0` | `1` — брать адрес клиента из `X-Forwarded-For` (крайний правый) |
| `SELFSYNC_RATE_REDEEM_ATTEMPTS` | `10` | неверных кодов подключения с одного адреса за окно |
| `SELFSYNC_RATE_REDEEM_WINDOW` | `15m` | окно подсчёта для кодов |
| `SELFSYNC_RATE_REDEEM_BLOCK` | `15m` | блокировка адреса после порога |
| `SELFSYNC_RATE_REDEEM_GLOBAL` | `200` | неверных кодов со всех адресов за то же окно; сверх порога — одна попытка в минуту |
| `SELFSYNC_RATE_AUTH_ATTEMPTS` | `30` | отвергнутых токенов (401) с одного адреса за окно |
| `SELFSYNC_RATE_AUTH_WINDOW` | `1m` | окно подсчёта для токенов |
| `SELFSYNC_RATE_AUTH_BLOCK` | `1m` | блокировка адреса после порога |

В TOML лимиты задаются в секции `[rate]` теми же именами в нижнем регистре без префикса (`redeem_attempts = 10`, `auth_window = "1m"`), `trusted_proxy = true` — ключ верхнего уровня. Порог `0` отключает соответствующий лимит; окно и блокировка — не меньше секунды, иначе сервер не стартует.

**Лимит неудачных попыток.** Коды и токены перебором не берутся, но сканер не должен грузить SQLite и выглядеть в журнале как обычная работа. Сервер считает только неудачи (неверный код подключения, отвергнутый токен) и по достижении порога отвечает `429` с `Retry-After`; плагин и консольный клиент выжидают это время без повторов. Счётчики лежат в `server.db`, поэтому работают и в CGI; `selfsync sweep` удаляет те, что не менялись сутки. Запросы без токена не считаются. Адрес клиента — адрес соединения (в CGI — `REMOTE_ADDR`). За обратным прокси в режимах `serve`/`socket` все запросы приходят с адреса прокси: включите `SELFSYNC_TRUSTED_PROXY=1` и пусть прокси передаёт адрес (конфиги в [deploy/](deploy/) это уже делают). Без прокси, перезаписывающего заголовок, флаг включать нельзя: адрес сможет выбрать кто угодно. Если адрес неизвестен (Unix-сокет без доверенного прокси), у всех клиентов один общий счётчик.

### Служебные команды

```sh
selfsync token add --vault notes --name laptop   # токен устройства (vault создаётся сам)
selfsync link --vault notes --name phone         # одноразовая ссылка + QR в терминале
selfsync token add --vault notes --name nas --read-only   # получает изменения, отправлять не может
selfsync token list | revoke --name phone
selfsync vault list
selfsync import --vault notes --from ~/Notes     # залить существующую папку
selfsync backup /backups/selfsync-$(date +%F)    # консистентная копия на ходу
selfsync gc --vault notes                         # план сборки мусора; --yes — выполнить
selfsync sweep                                    # стереть удалённое старше окна хранения (таймер)
selfsync verify                                   # проверка целостности: базы, хэши блобов, отсутствующие блобы (таймер)
selfsync healthcheck
```

Резервную копию делайте командой `backup`: она консистентна и при работающем сервере. Восстановление — просто вернуть каталог на место. Устройства заметят, что сервер «помолодел», и выполнят полную сверку, ничего не удаляя. На той же файловой системе `backup` не копирует блобы, а делает на них жёсткие ссылки. Это экономит место, но от порчи диска не спасает: повреждённый блоб окажется повреждён в обоих местах. Хотя бы одну копию держите на другом диске.

**Проверка целостности.** Тихо испорченный блоб иначе обнаружится, только когда какое-то устройство попробует его скачать, — может быть, через год. `selfsync verify` проверяет обе базы (`PRAGMA integrity_check`), пересчитывает SHA-256 каждого блоба (имя блоба — хэш хранимых байтов, и у зашифрованных тоже, так что ключ не нужен), ищет блобы, на которые ссылаются записи, но которых нет, и проверяет, что у зашифрованного vault'а есть читаемая запись ключа. Блобы без ссылок и брошенные загрузки только подсчитываются, убирает их `gc`. Код выхода: 0 — всё в порядке, 1 — найдены проблемы, 2 — проверку не удалось запустить. `--quiet` печатает только проблемы. Проверка только читает и безопасна на работающем сервере.

Испорченный или пропавший блоб можно взять из любого бэкапа: хранилище адресуется по содержимому, и в бэкапе тот же файл лежит под тем же именем — `selfsync verify --repair-from /backups/selfsync-2026-10-01`. Каждый файл из бэкапа сначала сверяется с хэшем; испорченный оригинал переносится в `quarantine/` в каталоге vault'а (`gc` его не трогает, `backup` копирует).

Юнит `selfsync-verify.timer` запускает проверку раз в неделю. При найденных проблемах служба падает и видна в `systemctl --failed`; уведомление можно повесить своим `OnFailure=`. Разовый запуск под `DynamicUser` и в Docker:

```sh
sudo systemd-run --pipe -p DynamicUser=yes -p User=selfsync -p StateDirectory=selfsync \
  /usr/local/bin/selfsync verify --repair-from /backups/selfsync-2026-10-01
docker compose run --rm selfsync verify
```

### Устройства только для чтения

Зеркало на сервере публикации, резервная копия на NAS, «читалка» на старом планшете: устройство, которое ничего не должно менять и токен которого при утечке не даёт записи.

```sh
selfsync token add --vault notes --name nas --read-only
selfsync link --vault notes --name tablet --read-only
```

В плагине — переключатель «Только чтение» под «Подключить новое устройство», перед созданием ссылки. Правило на сервере одно: устройству только для чтения разрешены только `GET` и `HEAD`. Значит, оно не может записывать файлы, менять срок хранения и ключ шифрования, отзывать устройства и создавать ссылки подключения. `token list` и список устройств в плагине помечают такие устройства.

Устройство получает всё, а собственные правки остаются на нём: в строке состояния — «Только чтение» и сколько локальных правок не уйдёт на сервер. Если файл, изменённый на нём, изменится и на другом устройстве, на место встаёт серверная версия, а локальная сохраняется копией рядом, как при конфликте, — молча ничего не теряется. Кнопки шифрования, срока хранения, отзыва и ссылок плагин скрывает. `selfsync-cli run --once` в такой папке завершается с кодом 0 и предупреждает о локальных правках, `status` показывает режим. Плагин и CLI 0.1.3 этого режима не знают: работают, но первая локальная правка превращается в ошибку синхронизации.

## Плагин Obsidian

### Установка

Из каталога сторонних плагинов Obsidian (поиск «Selfsync») или вручную: скопируйте `main.js`, `manifest.json` и `styles.css` из релиза в `<vault>/.obsidian/plugins/selfsync/` и включите плагин в настройках Obsidian (раздел «Сторонние плагины»).

### Подключение

- **По ссылке или QR.** Выполните на сервере `selfsync link …` или нажмите «Подключить новое устройство» в настройках уже подключённого Obsidian. Откройте ссылку на новом устройстве (камера телефона распознаёт QR): страница сервера откроет Obsidian с готовыми полями.
- **По коду вручную** — команда «Подключиться к серверу».
- **Токеном** — адрес сервера и токен в настройках.

### Каждый день

- **Статус-бар:** ✓ синхронизировано, ↻ идёт синхронизация, ⚠ сервер недоступен, 🔒 нужен пароль, ⛔ синхронизация остановлена. Клик — синхронизировать сейчас (или ввести пароль, или переподключиться).
- **Синхронизация** идёт через 2–3 секунды после последней правки, при запуске, при возврате на передний план и по опросу. Если Obsidian уходит в фон, очередь отправляется сразу.
- **Конфликт** — уведомление, а в окне «Нерешённые конфликты» можно оставить обе версии, свою или серверную.
- **Удалённые файлы** — команда «Восстановить удалённые файлы» открывает корзину сервера.
- **История файла** — в контекстном меню файла или командой.

По умолчанию не синхронизируются `.obsidian/` (настройки различаются между устройствами) и `.trash/`. Исключения задаются в настройках.

### Телефоны: ограничения

На мобильных Obsidian читает файл только целиком (`readBinary`), поэтому очень большие вложения требуют столько же оперативной памяти. Лимит размера файла по умолчанию — 512 МиБ, но на телефоне разумно держать вложения заметно меньше. На десктопе большие файлы читаются частями.

Argon2id для пароля шифрования использует 64 МиБ памяти. На современных телефонах это проходит за секунды, но разблокировка один раз на устройстве займёт заметное время.

### Имена файлов на разных системах

Linux и macOS разрешают в именах `? : * " < > |`, а Windows и хранилище Android — нет (Windows вдобавок резервирует `CON`, `NUL`, `COM1` и подобные). Такой файл синхронизируется между устройствами, которые могут его хранить; на остальных он пропускается с уведомлением, а весь прочий vault синхронизируется как обычно. Устройство, где такое имя создали, тоже предупреждает. Чтобы файл появился везде, переименуйте его.

## Консольный клиент

`selfsync-cli` синхронизирует обычную папку тем же ядром: так можно держать копию vault'а на сервере или NAS или синхронизировать машину без Obsidian.

```sh
selfsync-cli connect --dir ~/notes --server https://notes.example.com --code КОД
selfsync-cli run --dir ~/notes            # следить за папкой до Ctrl-C
selfsync-cli run --dir ~/notes --once     # один цикл (cron); коды выхода: 1 — сеть, 2 — нужен пароль, 3 — устройство отозвано
selfsync-cli encrypt --dir ~/notes --password-file ~/.notes-pass
selfsync-cli status --dir ~/notes
```

История, корзина сервера и конфликты доступны и без Obsidian. Каждая такая команда сначала выполняет цикл синка (нужен актуальный индекс, а для зашифрованного vault'а — ключ: `--password-file` или `SELFSYNC_PASSWORD`, как у `run`); меняющие команды дожидаются ещё одного цикла, так что к их завершению результат уже на сервере. Коды выхода — как у `run --once`, `--json` даёт вывод для скриптов.

```sh
selfsync-cli history notes/plan.md          # ревизии: номер, время, размер, устройство
selfsync-cli revert notes/plan.md --rev 3   # неотправленная текущая версия остаётся копией рядом
selfsync-cli trash                          # удалённое на сервере и когда сотрётся (--all — и просроченное)
selfsync-cli restore notes/old.md
selfsync-cli purge notes/old.md --yes       # стереть из корзины окончательно, вместе с историей
selfsync-cli conflicts
selfsync-cli resolve 4 --keep mine          # both | mine | server
```

С папкой одновременно работает один процесс (`.selfsync/lock`): если `run` запущен службой, сначала остановите её (`systemctl --user stop selfsync-cli@notes`).

Служебные данные клиент хранит в `<папка>/.selfsync/` (токен и ключ с правами 0600), удалённое кладёт в `<папка>/.trash/`. Чтобы клиент работал службой, есть [deploy/systemd/user/selfsync-cli@.service](deploy/systemd/user/selfsync-cli@.service): `systemctl --user enable --now selfsync-cli@notes`.

**Команда после синка.** `run --exec CMD` (или `exec = "..."` в `.selfsync/config.toml`) запускает `sh -c CMD` в папке после каждого цикла, который что-то изменил: коммит в git, сборка Quartz или Hugo, бэкап.

```sh
cd ~/notes && git init
selfsync-cli run --dir ~/notes --exec 'git add -A && git commit -qm "selfsync: $SELFSYNC_PULLED in, $SELFSYNC_PUSHED out" || true'
selfsync-cli run --dir ~/site --exec 'npx quartz build' --exec-timeout 30m
```

Хук получает `SELFSYNC_DIR`, `SELFSYNC_PULLED` (сколько путей синк изменил здесь), `SELFSYNC_PUSHED` (сколько отправил) и `SELFSYNC_CHANGES_FILE` — файл со всеми этими путями по одному на строку (у зашифрованного vault'а — расшифрованными). Хуки не накладываются: циклы, закончившиеся, пока хук работает, объединяются в один следующий запуск. Ненулевой код выхода и таймаут (`--exec-timeout`, по умолчанию 10 минут; останавливается вся группа процессов) пишутся в журнал и синк не останавливают. С `--once` хук успевает выполниться до выхода, а код выхода от него не зависит. `.git/` исключён по умолчанию в конфигах, созданных этой версией; для старого конфига `status` предупреждает, если в папке есть `.git`, который уйдёт на устройства.

## Шифрование

Шифрование включается из настроек плагина или командой `selfsync-cli encrypt` на уже работающем vault'е. Существующие файлы перезаливаются зашифрованными, после чего открытые копии на сервере стираются. Сервер видит только шифртекст содержимого и имён, размеры и время изменений. Пароль не восстанавливается: без него копию на сервере не прочитать (локальные файлы на устройствах остаются). Модель угроз и чего шифрование не скрывает — в [SECURITY.md](SECURITY.md).

## Разработка

```sh
cargo test --workspace                                   # ядро, сервер, клиент, сценарии синка
cargo run --release -p selfsync-sim -- --runs 10000      # детерминированная симуляция со сбоями
./scripts/build-wasm.sh                                  # ядро → plugin/pkg (бюджет 1,5 МБ)
cargo build -p selfsync-server
cd plugin && npm ci && npm run build && npm test         # плагин: типы, сборка, e2e против сервера
```

Падение симуляции воспроизводится по seed: `selfsync-sim --seed N --runs 1`; полная трасса — с `SIM_FULL_TRACE=1`.

```

  selfsync-wasm    ядро для плагина
  selfsync-cli     консольный клиент
  selfsync-sim     симуляция: клиенты + настоящий сервер + сбои; сценарии 13.2
plugin/            плагин Obsidian (TypeScript, esbuild)
deploy/            systemd, Caddy, nginx, Docker, Podman
spec/              план, архитектура, протокол, решения
```

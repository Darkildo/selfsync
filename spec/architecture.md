# Архитектура notesync

Для тех, кто будет менять код. Протокол — в [protocol.md](protocol.md), причины решений — в [decisions.md](decisions.md).

## Части системы

| Крейт / каталог | Роль | Ввод-вывод |
|---|---|---|
| `notesync-proto` | типы протокола, сгенерированные из `.proto` | нет |
| `notesync-core` | всё, что касается синка: пути, формат блоба, шифрование, 3-way merge, индекс клиента, движок | нет (sans-IO) |
| `notesync-server` | HTTP API, SQLite, хранилище блобов, режимы запуска, служебные команды | да |
| `notesync-wasm` | ядро для плагина через wasm-bindgen | нет |
| `plugin/` | плагин Obsidian: исполнитель действий ядра, события vault'а, интерфейс | да |
| `notesync-cli` | консольный клиент: исполнитель на tokio и `std::fs` | да |
| `notesync-sim` | детерминированная симуляция: клиенты + настоящий сервер + сбои | фейковый |

Правило: **логика синка существует в одном экземпляре — в ядре.** Плагин и консольный клиент не принимают решений о том, что отправлять, что скачивать и как разрешать расхождения: они исполняют действия ядра и честно сообщают результат. Поэтому симуляция, которая гоняет то же ядро, проверяет поведение всех клиентов сразу.

## Ядро: движок

```
            Event                          Action
 хост ────────────────▶ Engine::handle ────────────────▶ хост
 (Start, Changed,        (now, event)     (Http, Read, Write, Trash,
  Done{id,result},                         SaveIndex, Wake, Status,
  Tick, SyncNow, …)                        Notify, …)
```

Снаружи движок — чистая функция от времени и события к списку действий. Действия с `id` ждут ответа `Event::Done { id, result }`. Остальные (`Wake`, `Status`, `Notify`, `Log`, `RememberKey`) — указания хосту. Время приходит с каждым событием, а внутреннее время только растёт: часы устройства могут прыгать.

Внутри логика написана обычным последовательным async-кодом (`engine/sync.rs`, `push.rs`, `pull.rs`, `resolve.rs`, …). Задачи крутит маленький исполнитель (`engine/runtime.rs`): каждое действие ввода-вывода — это future, который завершается, когда хост пришлёт `Done`. Рантайма и потоков нет, поэтому код собирается под wasm32 и детерминирован. Состояние лежит в `Rc<RefCell<State>>`; заимствование не держится через `.await`.

### Цикл синка

`sync::run_cycle`:
1. Если на устройстве осталась незаконченная миграция на шифрование, она продолжается первой.
2. **Скан** (`scan.rs`): полный обход при старте, возврате на передний план и раз в `full_scan_ms`, в остальное время — только пути из событий. Файл перехэшируется, только если изменились размер или mtime. Здесь же: распознавание переименований (пропал файл + появился с тем же хэшем), приведение имён к NFC, доведение прерванных двухшаговых переименований и записей.
3. **Проверка режима vault'а** (`changes?limit=1`): нельзя отправлять открытый текст в только что зашифрованный vault.
4. **Push** (`push.rs`): план (папки → переименования → содержимое → удаления), загрузка недостающих блобов, `ops`. Ответы разбираются в `resolve.rs`.
5. **Pull** (`pull.rs`): дельта по курсору; затем папки, переименования, файлы, tombstone'ы. Курсор сдвигается только после всей пачки и не уходит за запись, которую не удалось применить (`hold_seq`).
6. Ещё один push — для того, что изменилось при разрешении расхождений (результат слияния, восстановленные файлы).

Планирование (`engine/mod.rs`): debounce после правок, адаптивный опрос (интервал растёт в простое и сбрасывается при активности), long-poll `/v1/wait` с автоматическим отключением на CGI, backoff при ошибках. Всё это выражается через `Action::Wake`.

### Разрешение расхождений (`resolve.rs`)

Главный инвариант: ни одна версия текста не исчезает молча.
- **Правки в разных местах** — diff3 (`merge.rs`, только текст до 1 МиБ). Результат записывается локально и уходит следующим push.
- **Пересекающиеся правки, бинарные файлы, большие файлы** — обе версии: серверная на месте, локальная копией `имя (conflict ДАТА ВРЕМЯ устройство)`.
- **Два устройства создали один путь** — копия `имя (устройство ДАТА)` без записи конфликта.
- **Правка против удаления** — побеждает правка.
- **Правка против переименования** — правка идёт за файлом.

### Индекс клиента (`index.rs`)

На каждый путь — `FileState`:
- база: ревизия, хэш блоба и хэш открытого текста на сервере, от которых сделана локальная версия;
- последнее наблюдение локального файла;
- серверный путь, если переименование ещё не отправлено;
- незавершённая передача;
- признак «Put отправлен, ответ не получен» (`pending_put`).

Плюс курсор, режим шифрования, нерешённые конфликты, чекпоинт миграции и кэш базовых версий для слияния. Снимок сохраняется после каждого файла (`Action::SaveIndex`), так что процесс можно убить в любой момент. Формат: postcard с заголовком и версией; эталон v1 заморожен в тестах.

## Сервер

- `api/` — маршруты (axum), авторизация по токену, учёт активности для выхода по простою.
- `db/server.rs` — `server.db`: устройства, токены (SHA-256), коды подключения.
- `db/vault.rs` — по одной базе `meta.db` на vault: таблица `files` (текущее состояние путей = лог по seq), `revisions` (история), метаданные (ключ, маркер миграции, окно хранения, `purged_seq`). Здесь вся семантика операций (раздел 6.3 ТЗ).
- `blobs.rs` — хранилище блобов по хэшу (`blobs/<первые два символа>/<hash>`), загрузки частями, отдача с Range.
- `modes/` — `serve` (TCP или Unix), `socket` (systemd, выход по простою), `cgi` (один запрос на процесс).
- `cmd.rs`, `gc.rs`, `sweep.rs` — служебные команды.

SQLite работает в WAL с `busy_timeout`. Параллельные CGI-процессы пишут в одну базу через `BEGIN IMMEDIATE`, и seq остаётся строго монотонным (это проверяют тесты режимов).

## Форматы

- **Блоб NSB** (`blob.rs`). Открытый блоб — сам файл. Зашифрованный — заголовок, затем content_id, затем чанки по 1 МиБ, у каждого свой nonce и тег; небольшой текст перед шифрованием сжимается lz4.
- **Ключи** (`crypto.rs`). Мастер-ключ обёрнут Argon2id-ключом из пароля; подключи выводятся через HKDF; имена шифруются AES-SIV посегментно.

## Плагин

```
vault.on(create|modify|delete|rename) ─┐
visibilitychange ──────────────────────┤
статус-бар, команды, окна ─────────────┼─▶ Runner ──▶ WasmEngine.handle
setTimeout (Wake) ─────────────────────┘     │
                                             ▼
                                        Executor ──▶ FileBackend (Node fs | vault.adapter)
                                                 └─▶ HttpBackend (requestUrl)
```

- `engine.ts` (`Runner`) доставляет события в ядро, запускает действия и взводит таймер. Wake ядро шлёт только при изменении момента, поэтому таймер дополнительно сверяется с `nextWake()`.
- `executor.ts` выполняет действия по контракту `types.rs`: условия записи, `Precondition` / `NotFound`, настоящие имена файлов.
- `io/node.ts` — десктоп: атомарная замена через rename, fsync, чтение частями.
- `io/adapter.ts` — телефоны: атомарная запись по протоколу commit-фазы (adapter.rename не заменяет файл), докачка через `appendBinary`.
- `main.ts`, `settings.ts`, `ui/` — интерфейс, тексты в `i18n.ts`.
